# 10 · 故事技术栈定义（Story Tech Stack）

> 目的：把「Lux3D 资产 → 3D 叙事空间」的完整技术路线**定义成一套可复用的故事生产线**，
> 对标案例：[zork-underground-empire](https://github.com/emollick/zork-underground-empire)
> （Ethan Mollick 用 GPT-6 Astra 把 1977 年 Zork I 改编为浏览器 3D 冒险：保留原版剧情/谜题/文案，
> Three.js 纯静态前端，campaign/inventory-use/darkness 等模块化 + 全套单测）。
> 归属：T-019（Owner 授权 ZCode 主写；DSH 复核可回滚）。最后更新：2026-11-04 · ZCode

---

## 0. 一句话

**故事 = 数据（story-bible）+ 纯函数状态机（applyAction）+ 声明式条件（ObjectConditions）**；
资产 = Lux3D 生成 → Blender 修整组装（P1）→ gltf-transform 压缩；
呈现 = R3F 场景 + HTML overlay 文案；智能 = FastAPI + pgvector 检索/问答；存档 = localStorage + 服务端槽位（P2）。

```
Lux3D 生成物件 → Blender 修整和组装 → gltf-transform 压缩 → Three.js/R3F 展示与交互
→ Zustand 管理状态 → 后端和数据库负责检索、问答与存档
```

## 1. 六层架构

### L1 资产生产层（pipeline/）

| 环节 | 现状 | 契约 |
|---|---|---|
| Lux3D 两段式生成 | ✅ 17/17（文生图 G1-Turbo → 图生 3D G1，`generate-assets.mjs` 断点续跑） | `assets-manifest.json` 单一事实源；runs/ 归档证据链（glbTaskId） |
| **Blender Python 修整组装** | ⬜ **P1 待接入**（本机未装 Blender；装 4.x LTS 后启用） | headless `bpy` 脚本放 `pipeline/blender/`：①原点归底部中心 ②Z-up→导出 +Y Up ③命名规范 `SM_<zone>_<name>`/`UCX_` 前缀（详见 docs/01 §11.3）④面数校验 ≤15k（hero ≤30k）⑤part_split 部件组装（T-011 拆分动画的资产前置）。管线集成方式：manifest 增加可选 `blenderPost` 步骤，`blender --background --python` 调用；未安装时自动跳过并 warn（不阻塞现有直通路径） |
| gltf-transform 压缩 | ✅ quantize + simplify 0.35 + WebP 1024，-89% | 不用 Draco（保持零 CDN 外链） |

### L2 场景交互层（demo/src/scene/ + interaction.ts）

- E 键情境交互（Zork 同款）：视线/距离/朝向评分 → 交互候选 → dispatch；
- `SceneObjectDef` 声明式条件（conditions/visibleWhen/blockedText）＝ Zork 的「世界响应规则」数据化；
- GLB 优先 + 程序化兜底三层（HEAD 探测/Suspense/ErrorBoundary）——资产永远不能弄坏游戏。

### L3 故事脚本层（data/narrative.ts + data/scene.ts，本轮定型为「story-bible」契约）

**核心原则（继承 Zork/Infocom）：文案全部是数据，逻辑全部在状态机，两者用 ID 连接。**

| 数据块 | 结构 | 渲染规则 |
|---|---|---|
| 阶段 `STAGE_META` | `Record<Stage,{title,objective}>` | stage effect 推送 HUD 目标 |
| 进房 `ZONE_ENTER_LINES`（重访）+ `ZONE_FIRST_ENTER_LINES`（首访，T-019 新增） | `Record<ZoneId,string[]>` | `enterZone` 按 `visited` 选表（Zork「房间描述」机制） |
| 物件 `OBJECT_SUCCESS` | `Record<objectId,string[]>` | 交互成功时逐行 narration |
| 拦截 `blockedText`/`BLOCKED_DEFAULT`/`DIAL_WRONG_TEXTS` | Zork 式温和拒绝文案 | 条件不满足时 |
| 收集 `JOURNAL_ENTRIES`（12 条，手稿日记） | `Record<id,{id,title,text}>` | journal effect；UI 显「x/12」进度（T-019） |
| 提示 `HINTS` | `Record<Stage,[L1,L2,L3]>` | request_hint，三级逐具体 |
| 谜题 `use_item_on`（T-019 新增） | 物品×物件组合（如 brass_key×basin） | 新 Action 分支，错误组合温和失败不消耗 |
| 知识 `KNOWLEDGE_BASE`（18 条） | id/zoneId/objectId/cameraId/topics/sources/confidence | 档案检索 + Agent 引用，sources/confidence 必填（不编造） |

**后端下发形态**（文件头既有承诺的落地）：上述各表本身就是可 JSON 化的契约；
P2 时 server 以 `/api/story/bible` 下发同构 JSON，前端 `narrative.ts` 退化为远端数据的本地镜像。

### L4 状态层（game/）

- `applyAction(state, action) → {state, effects, ok}` 纯函数＝唯一剧情入口（Zork `campaign.ts` 同构）；
- Action 12 种（T-019 +`use_item_on`）、Effect 9 种；阶段单调（STAGE_INDEX）；
- Zustand 只做分发与运行时 UI 状态，UI/Agent 不得直改 stage/flags/inventory；
- **扩展规则**：新机制＝新 Action case + 新数据表；主线 7 步/9 flags/既有单测语义不可动（测试是契约的护栏）。

### L5 后端层（server/，FastAPI + PostgreSQL/pgvector）

| API | 职责 | 现状 |
|---|---|---|
| `/api/knowledge` | 检索：mock 内存过滤（13/13 E2E ✅）→ pg 模式 pgvector 语义检索 | pg 仅 DDL，P2 |
| `/api/agent` | 7 工具 function-calling（与前端 AGENT_TOOLS 同 schema），LLM 接入点 | 规则引擎 stub |
| `/api/save` | 服务端存档槽位（跨设备） | P2 规划 |

### L6 协同验收层（collab/）

文件即任务板（board.json + cli.mjs + handoffs）+ 门禁：`pnpm build` + 状态机单测（21+新增）+ GLB HEAD + 截图 + 密钥扫描。每个故事机制改动必须带新单测（继承 Zork 「campaign/puzzle/save/route 各有测试」的组织方式）。

## 3. 数据流全景

```
assets-manifest.json ─(Lux3D API)→ raw GLB ─(Blender P1)→ 修整 GLB ─(gltf-transform)→ public/models/*.glb
                                                                      ↓ 自动重写
                                                             assetRegistry.ts（17 条）
player E/键位 → dispatch(Action) → applyAction 纯函数 ─┬→ GameState（Zustand→localStorage 自动存档）
                                                       └→ Effect[] → narration/journal/sound/stage/darkness/…
narrative.ts(文案表) ←ID→ scene.ts(对象/条件/相机) ←ID→ knowledge.ts(检索) ←→ server /api/*(P2)
```
