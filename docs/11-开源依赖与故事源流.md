## 3. GitHub 检索 × Agent 搭配（消化 WorkBuddy §3）

四层检索法即 Agent 工具化管线：**发现**（`gh api search/repositories`，限定符 ≤3 防归零）→ **前置筛选**（`license:/topic:/org:/archived:false` 写进模板）→ **精确复核**（NOASSERTION ≠ 无协议，须读 `contents/LICENSE*` 原文）→ **持续监控**（Actions 定时比对三列差异）。
配套 ai-plugins 子代理映射（引用≠已启用）：`dependency-reviewer`（引入新 OSS 依赖时审协议/漏洞）、`oss-upgrade-investigator`（升级评估）、`findings-browser`（结果浏览）。

## 5. ink 对接评估（零代码结论）

**事实基线**：ink（MIT）是叙事脚本语言，inklecate 编译为 JSON 节点流；inkjs（MIT，本次复核）是浏览器运行时。我方契约是 `Record<id,结构化文案>` 扁平表 + `applyAction` 纯函数选表（事件驱动，非节点流驱动）。

| 路径 | 内容 | 判定 |
|---|---|---|
| ①knot→id 映射 | 约定 `:: zone_basement_first`、`:: object_success_<id>` 等 knot 命名，编译后按 knot 抽文本块转为扁平表 | **可行**，且与现有契约零冲突（ink 的 visit 计数与我方 visited 驱动同构） |
| ②inkjs 作运行时 | 新增 ~200KB 依赖 + ink 变量与 GameState flags 双轨漂移 + 侵蚀「applyAction 唯一剧情入口」红线 | **不推荐**：违反文案/逻辑分离原则；须 DSH 批准 + 契约改造 |
| ③**创作期工具（推荐）** | inky/ink 仅创作阶段用：作者（或 LLM Agent）写 .ink 分支草稿 → inklecate 编译 JSON 校验语法 → 转换脚本（Node，放 `pipeline/story/`）按 knot 约定生成 `narrative.ts` 表段（或后端 JSON） | **运行时零依赖、零契约改动、27 单测不动**；LLM 产出 .ink 比直接产出 TS 更安全（语法可机器校验） |

**采纳③所需的板上流程**（届时）：add 任务（scope: pipeline/story + demo/src/data）→ inklecate 以外不新增运行时依赖 → 转换产物过 27 单测 + 文本量断言 → DSH verify。
**不采纳的替代路径**：维持现状（手写 `narrative.ts` + T-015 文风约定），后端 JSON 下发（docs/10 §L3 既有承诺）已覆盖「文案与代码分离」诉求。
